 ### API для работы с кучей
- `malloc(n)` - выделить память;
- `free(ptr)` - освободить память;
- `realloc(ptr, n)` - перевыделить память;
- `calloc(memb, size)` - выделить занулённый.
При выделении области памяти glibc возвращает чанк памяти.

### Структура чанка 
Структура чанка зависит от его состояния (выделенный или освобождённый).
`malloc(n)` возвращает `&((char *)malloc_chunk)[0x10]` - смещение на 0x10 (16) байт.
Структура: 
- prev_size - размер предыдущего чанка (8 байт);
	- chunk_size - размер выделенного чанка (8 байт);
- user_data - данные.

В размере (chunk_size) 4 младших бита не используются для определения размера, т.к. выделение происходит по границе 16 байт.
Четыре младшие биты в размере:
- bit0 - prev_in_use;
- bit1 - is_mapped;
- bit2 - non_main_arena;
- bit3 - не используется, всегда 0.

При освобождении чанка туда записывается служебная информация.
Там остаётся:
- prev_size - размер предыдущего чанка;
- chunk_size - размер выделенного чанка;
- fd - адрес следующего чанка;
- bk - адрес предыдущего чанка;
- fd_nextsize
- bk_nextsize
 
### Сохранение свободных чанков
Имеется ряд специальных списков:
- **`fastbin`** - чанки размером `[0x20, 0x80]` включая заголовки. Является односвязcным списком. Адреса идут с маленьким шагом, лежат чанки с одинаковым размером;
- **`unsortedbin`** - любые чанки кроме выделенных через `mmap`. Является двусвязным списком;
- **`smallbin`** - чанки размером `[0x20, 0x400)`;
- **`largebin`** - чанки размером `[0x400, MMAP_THRESHOLD]`. Адреса лежат с большим шагом, поэтому хранятся в двух уровнях ;
- **`topchunk`** - используется, когда во всех списках выше ничего подходящего нет.
- **`tcache`** - добавлен в **libc-2.26**. Представляет собой 64 односвязных списка, которые хранят чанки размером `[0x20, 0x410]`. В каждом списке может быть максимум 7 элементов. Имеет мало проверок, т.к. реализовано для быстрой работы.

### Освобождение чанков
В новой версии libc (2.26) после освобождения чанки сначала попадают в tcache (64 односвязных списка).
- В каждом списке tcache максимум может быть 7 элементов.
- Для каждого размера (от 0x20 до 0x410) в tcache имеется свой список.
После заполнение списка в tcache последующие освобождённые чанки попадают в `fastbin` для чанков размера от 0x20 до 0x80 и в `unsortedbin` для остальных чанков.

# C++ классы
**Без виртуальных методов (Plain)**:
Объект — это просто структура с данными.
- **Смещение `+0`:** Первое поле данных.
- **Смещение `+N`:** Остальные поля в порядке объявления.
- _Размер:_ Сумма размеров всех полей + байты выравнивания (padding).
**С виртуальными методами (Polymorphic)**:
В начало добавляется скрытый указатель для работы полиморфизма.
- **Смещение `+0`:** **vptr** (8 байт) — адрес таблицы виртуальных функций (`vtable`).
- **Смещение `+8`:** Первое поле данных.
- **Смещение `+8+N`:** Остальные поля.

# Атаки на кучу

## Type Confusion
**Type Confusion** - это уязвимость, возникающая, когда программа обращается к объекту одного типа, используя методы или указатели, предназначенные для другого типа.
Программа не проверяет (или проверяет некорректно) соответствие типа объекта перед его использованием. Это приводит к нарушению типизации и неверной интерпретации содержимого памяти.
Если программа ожидает объект класса `Person`, но вместо него подсовывается объект `Meter`, функции `Person` могут принять данные из `Meter` за адреса в памяти или указатели на таблицы виртуальных функций (vtable).
Пример: [Accounter](pwn/pwn.spbctf.ru/8.%20Type%20Confusion,%20Use-After-Free,%20Double%20Free/Accounter.md), [Confusion Hall](pwn/pwn.spbctf.ru/8.%20Type%20Confusion,%20Use-After-Free,%20Double%20Free/Confusion%20Hall.md).

## Use-After-Free
**Use-After-Free** — это уязвимость, возникающая при попытке обращения к объекту через указатель после того, как память, на которую он ссылается, была помечена как свободная (освобождена).
**Type Confusion (через UAF):** возникает при аллокации нового объекта со специфической структурой в тот же адрес. При обращении по старому указателю программа интерпретирует данные нового объекта как поля исходного.
Пример: [Liberal Executor](pwn/pwn.spbctf.ru/8.%20Type%20Confusion,%20Use-After-Free,%20Double%20Free/Liberal%20Executor.md), [UAF Fun House](pwn/pwn.spbctf.ru/8.%20Type%20Confusion,%20Use-After-Free,%20Double%20Free/UAF%20Fun%20House.md).

## Double Free
**Double Free** — уязвимость, возникающая при повторном вызове функции освобождения памяти (`free`) для одного и того же указателя без промежуточной аллокации.
**Type Confusion (через Double Free):** возникает при зацикливании связного списка аллокатора (fastbins/tcache), что позволяет дважды получить один и тот же адрес через `malloc`.
Но на новых версиях libc есть защита от double free.
Метод обхода защиты:
1. Аллоцировать 9 разных объектов;
2. Освободить память 7-ми объектов;
3. Освободить: №8, №9, №8;
4. Аллоцировать 7 ненужных объектов;
5. Аллоцировать A, B, C.
По итогу A и С указывают на одну и ту же память.
Пример: [Wishlist](pwn/pwn.spbctf.ru/8.%20Type%20Confusion,%20Use-After-Free,%20Double%20Free/Wishlist.md), [Just2Free](pwn/pwn.spbctf.ru/8.%20Type%20Confusion,%20Use-After-Free,%20Double%20Free/Just2Free.md).

## libc RCE
Главная задача - положить чанк в unsorted bin, первый чанк, который там оказывается гарантированно ссылается на адрес внутри libc из которого можно высчитать адреса всех остальных функций и данных внутри библиотеки.
Как получить адрес:
1. Выделить чанк размером более 0я400 (0x70, если libc без tcache);
2. Выделить guard chunk, чтобы чанк не замержило с top chunk;
3. Освободить первый чанк - он начинает указывать в main_arena;
4. Варианты прочитать адрес:
	1. Через UAF fd/bk освобождённого чанка;
	2. Выделить чанк и прочитать (если можно избежать инициализации).
Далее в libc можно переписать адреса `__malloc_hook`,  `__free_hook` (удалены в glibc >= 2.34) или подобный на адрес указатели функции которые будут вызываться вместо них, например, заменить `__free_hook` на `system` или `__malloc_hook` на `one_gadget`.
Пример: [leak and write](pwn/pwn.spbctf.ru/9.%20Внутреннее%20устройство%20кучи/leak%20and%20write.md), [leak and write2](pwn/pwn.spbctf.ru/9.%20Внутреннее%20устройство%20кучи/leak%20and%20write2.md)

## Атаки на tcache
tcache - односвязный список, в котором все основные проверки происходят при добавлении, если что-то там появилось, то без проблем отдастся.
Главная цель - перетереть fd, чтобы при следующем `malloc` чанк создался по этому адресу.
libc < 2.30:
1. Ликаем адрес `libc`;
2. Выделяем чанк и кладём в tcache;
3. Перетираем next на `__free_hook`;
4. Выделяем чанк;
5. Выделяем ещё 1 и переписываем первые 8 байт на адрес `system`;
6. `free(&"/bin/sh")`.
libc >= 2.31:
7. Выделяем чанки `a`, `b`;
8. `free(a)`, `free(b)`;
9. Перетираем next у `b` на `__free_hook`;
10. Выделяем чанк;
11. Выделяем ещё 1 и переписываем первые 8 байт на адрес `system`;
12. `free(&"/bin/sh")`.
Изменения в подходах связаны с тем, что начиная с версии 2.31 libc считает количество элементов, которые должны лежать в tcache, при каждом добавлении счётчик увеличивается, когда происходит `malloc` от туда, то счётчик уменьшается. Если счётчик равен 0, то он даже не смотрит туда, т.к. знает, что там ничего быть не должно.
