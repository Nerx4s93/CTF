SQLi на основе ошибок относятся к случаям, когда есть возможность использовать сообщения об ошибках для извлечения или получения информации из базы данных. Возможности зависят от конфигурации базы данных и типов ошибок:
- Можете заставить приложение вернуть определённый ответ с ошибкой на основе результата логического выражения. Это можно эксплуатировать так же, как и условные ответы.
- Можете вызвать сообщения об ошибках, которые выводят данные, возвращаемые запросом. Это фактически превращает в остальном слепые уязвимости SQL-инъекций в видимые.

## Эксплуатация слепых SQL-инъекций путём вызова условных 

Некоторые приложения выполняют SQL-запросы, но их поведение не меняется независимо от того, возвращает ли запрос какие-либо данные.

Часто удаётся заставить приложение вернуть другой ответ в зависимости от того, возникает ли ошибка SQL. Можете изменить запрос так, чтобы он вызывал ошибку базы данных только в том случае, если условие истинно.

Чтобы понять, как это работает, предположим, что поочерёдно отправляются два запроса, содержащие следующие значения cookie TrackingId:
```
xyz' AND (SELECT CASE WHEN (1=2) THEN 1/0 ELSE 'a' END)='a
xyz' AND (SELECT CASE WHEN (1=1) THEN 1/0 ELSE 'a' END)='a
```
Эти входные данные используют ключевое слово CASE для проверки условия и возврата различных выражений в зависимости от того, истинно ли это выражение:
- В первом случае выражение CASE вычисляется как 'a', что не вызывает никакой ошибки.
- Во втором случае оно вычисляется как 1/0, что вызывает ошибку деления на ноль.

Если ошибка приводит к различию в HTTP-ответе приложения, вы можете использовать это для определения того, истинно ли внедрённое условие.

Используя эту технику, можете извлекать данные, проверяя по одному символу за раз:
```
xyz' AND (SELECT CASE WHEN (Username = 'Administrator' AND SUBSTRING(Password, 1, 1) > 'm') THEN 1/0 ELSE 'a' END FROM Users)='a
```

## Извлечение данных через подробные сообщения об ошибках SQL

Неправильная конфигурация базы данных иногда приводит к появлению подробных сообщений об ошибках.

### Leak запроса

Например, следующее сообщение об ошибке, которое возникает после внедрения одинарной кавычки в параметр `id`:
```
Unterminated string literal started at position 52 in SQL SELECT * FROM tracking WHERE id = '''. Expected char
```

Здесь показан полный запрос, который приложение построило с использованием наших входных данных. Мы видим, что в данном случае мы внедряемся в строку, заключённую в одинарные кавычки, внутри оператора `WHERE`. Это упрощает построение корректного запроса.

### Leak часть данных

Иногда может удаться заставить приложение сгенерировать сообщение об ошибке, которое содержит часть данных, возвращаемых запросом.

Для этого можно использовать функцию `CAST()`. Она позволяет преобразовывать один тип данных в другой. Например, представьте запрос, содержащий следующее выражение:
```
CAST((SELECT example_column FROM example_table) AS int)
```

Часто данные, которые нужно прочитать, являются строкой. Попытка преобразовать их в несовместимый тип данных, например в `int`, может вызвать ошибку, подобную следующей:
```
ERROR: invalid input syntax for type integer: "Example data"
```
Этот тип запроса также может быть полезен, если ограничение на количество символов не позволяет вам вызывать условные ответы.
